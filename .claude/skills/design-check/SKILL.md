# DESIGN.md 진단

`node scripts/design-check.mjs $ARGUMENTS` 를 실행합니다.

## 기계가 보는 것

| 층 | 점검 |
|---|---|
| 겉모습 (1층) | 컬러 토큰, 타이포그래피, 간격과 모서리, 컴포넌트 규격 |
| 행동 (2층) | 상태 규칙(빈, 오류, 처리 중, 불가), 카피 톤, 문구 예시, 접근성 또는 움직임 |
| 검증 (3층) | 숫자로 쓴 규칙, 금지 사항, 글자와 바탕 대비, 버전 표기, 모호한 표현, 알려진 빈칸 |

머리말(YAML)에 `components` 가 있으면 컴포넌트마다 적힌 글자색과 바탕색 조합을 그대로 잽니다. 12px 미만 글자 토큰과 높이 44px 미만 컴포넌트는 점수에 넣지 않고 "참고 수치"로 적습니다.

## 보고하는 순서

끝나면 `04_deliver/reports/design-check.md` 를 읽고 이렇게 보고합니다.

1. 세 층의 채움 정도를 표로.
2. 빠진 항목을 쉬운 말로. 예: "빈 상태일 때 화면이 무엇을 보여 줘야 하는지 적혀 있지 않아요."
3. "확인할 수 없는 표현"이 있으면 줄 번호와 문장을 보여 주고, 문장마다 **고쳐 쓴 안 한 가지**를 나란히 제안합니다. 예: "적절한 여백" 은 "요소 사이 8 / 12 / 16 / 24 중에서".
4. "대비가 부족한 컴포넌트"나 "참고 수치"가 있으면 표로 보여 주고, 줄마다 그대로 둘지 고칠지 사용자에게 묻습니다. 남의 사이트를 관찰해 만든 파일은 그 사이트의 약점도 함께 적혀 있을 수 있습니다.
5. 빠진 항목마다 **사용자에게 물어볼 질문 한 개**. 답을 지어내지 않습니다. 예: "장바구니가 비었을 때 가장 먼저 보여 주고 싶은 것은 무엇인가요?"
6. 가장 먼저 할 일 한 가지를 고릅니다. 리포트의 "다음에 할 일" 첫 줄을 기준으로 합니다.
7. 이 진단이 보지 못하는 것 한 줄: 규칙이 옳은지, 우리 브랜드다운지는 사람이 판단합니다.

## 지킬 것

- 문서를 직접 고치지 않습니다. 사용자가 질문에 답하거나 고쳐 쓴 안을 고르면, 승인을 받은 뒤에 DESIGN.md 의 알맞은 구역에 넣습니다.
- 넣은 뒤에는 버전 줄과 `바뀐 기록` 에 한 줄을 더하고, 진단을 다시 실행해 결과가 달라졌는지 보여 줍니다.
- 남의 레퍼런스 파일을 진단했다면 "이 파일에서 빌려 올 것"과 "우리가 직접 채워야 하는 것"을 나눠서 말합니다.
- 받은 파일(`00_inputs/reference/`)은 고치지 않습니다. 남길 값만 사용자의 승인을 받아 `DESIGN.md` 로 옮깁니다.
- 점수가 가득 찼다고 좋은 문서라고 말하지 않습니다. 이 진단은 적혀 있는지만 봅니다.
