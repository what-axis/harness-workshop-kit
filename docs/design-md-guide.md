# DESIGN.md 작성 가이드

AI가 읽는 디자인 규칙 문서를 실무에서 쓸 수 있게 만드는 법입니다. 공개된 레퍼런스 파일(무료와 유료)을 뜯어본 결과에서 출발합니다.

조회 기준일: 2026-11-22. 가격과 구성은 바뀔 수 있으니 쓰기 전에 각 사이트에서 다시 확인하세요.

## 1. DESIGN.md 는 무엇인가

- 디자인 시스템을 한 파일의 글로 적어, 코딩 에이전트가 화면을 만들기 전에 읽게 하는 문서입니다.
- Google 의 디자인 도구 Stitch 에서 쓰던 형식이고, 2026년 4월 21일 Google Labs 가 사양 초안을 공개했습니다(현재 alpha).
- 두 겹으로 되어 있습니다. 맨 위의 YAML 토큰(기계가 읽는 정확한 값)과 아래의 글(왜 그렇게 쓰는지). 사양은 "토큰이 기준값이고 글은 적용 맥락"이라고 정리합니다.
- 사양이 정한 구역 순서: Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Motion, Voice & Content Strategy, Components, Do's and Don'ts. 모두 선택이고, 모르는 제목이 있어도 오류가 아닙니다.
- 검사 도구: `npx @google/design.md lint DESIGN.md` (구조 오류, 끊어진 토큰 참조 등).

## 2. getdesign.md 무료와 유료의 차이

getdesign.md 는 공개 모음집 awesome-design-md(VoltAgent, MIT)를 둘러보는 사이트입니다. 유명 웹사이트의 공개 페이지를 분석해 DESIGN.md 로 정리한 파일을 모아 둡니다. 해당 브랜드의 공식 문서가 아니라 제3자의 분석입니다.

| | 무료 | Private DESIGN.md | Catalog Pass | Website Starter Kit |
|---|---|---|---|---|
| 값 | 0 | 39달러, 한 번 (정가 59) | 월 99달러 | 249달러, 한 번 (정가 299) |
| 대상 | 유명 브랜드 세트. 깃허브 저장소 기준 84개 | 내가 지정한 사이트 한 곳 | 큐레이션된 랜딩 페이지 분석 40여 개, 매달 추가 | 내 사이트용 비공개 DESIGN.md 포함 |
| 받는 것 | DESIGN.md, 라이트·다크 미리보기 | DESIGN.md(라이트+다크), 테마 미리보기 HTML, 비공개 채널 | 카탈로그의 유료 표시 항목 열람 | 인증, 결제, AI 채팅, 블로그, 문서, 이메일, 분석이 연결된 실제 코드 |
| 공개 여부 | 누구나 | 요청자에게만 이메일 전달 | 구독자 | 구매자 |
| 설치 | `npx getdesign@latest add 이름` 또는 내려받기 | 이메일 | 사이트 | 소스 코드 |

이 밖에 "DESIGN.md Pro"(AI로 웹사이트를 시각적으로 만드는 빌더)와 영상 템플릿, 배경 소재를 따로 팝니다. Catalog Pass 의 파일 수와 추가 주기는 비교 사이트의 10월 조회 값이고, 사이트 목록에는 550개 중 44개에 "Catalog Pass included" 표시가 있습니다.

### 유료가 파는 것

파일 형식은 같습니다. 돈을 내고 사는 것은 다음 네 가지입니다.

1. **대상을 고를 권리**: 목록에 없는 사이트, 내 사이트를 분석해 줍니다.
2. **비공개**: 결과가 공개 목록에 올라가지 않습니다.
3. **큐레이션과 갱신**: 누군가 고르고 계속 추가합니다.
4. **돌아가는 코드**: 스타터 킷은 문서가 아니라 제품 뼈대입니다.

### 무료 84개를 직접 뜯어본 결과

이 키트의 `scripts/design-check.mjs` 로 깃허브 저장소의 84개 파일을 전부 진단했습니다.

| 본 것 | 결과 |
|---|---|
| 겉모습 층(컬러, 타이포, 간격, 컴포넌트)이 다 있는 파일 | 74 / 84 (나머지 10개는 3 / 4) |
| 상태 규칙이나 카피 톤을 다루는 구역이 있는 파일 | 0 / 84 |
| "empty state"를 한 번이라도 언급한 파일 | 1 / 84 |
| 금지 사항(Do's and Don'ts)이 있는 파일 | 83 / 84 |
| 마케팅·랜딩 페이지를 근거로 삼았다고 읽히는 파일 | 79 / 84 |
| 스스로 "Known Gaps"를 적은 파일 | 45 / 84. 그중 42개가 상태(호버, 포커스, 오류, 로딩)를, 39개가 폼과 검증을 관찰하지 못했다고 적음 |
| 파일 크기 | 중앙값 약 28KB (4KB ~ 44KB) |

파일별 결과는 `docs/reference-84-result.csv` 에 있습니다.

읽는 법:

- 레퍼런스 파일은 **보이는 것**을 잘 담습니다. 색, 글자, 버튼 모양, 그림자, 하지 말아야 할 겉모습.
- **보이지 않는 것**은 비어 있습니다. 빈 화면, 오류 문장, 처리 중, 살 수 없는 상태, 문구의 말투. 공개된 랜딩 페이지만 보고는 알 수 없기 때문이고, 파일 스스로도 그렇게 적어 둡니다.
- 유료 파일을 직접 사서 열어 보지는 못했습니다. 판매 페이지의 설명으로는 분석 대상과 제공 방식이 달라질 뿐, "공개 페이지를 관찰해 쓴다"는 방법은 같습니다. 그래서 우리 제품의 상태 규칙과 문구 규칙은 유료로도 채워지지 않는다고 보는 것이 안전합니다.

## 3. 실무용 DESIGN.md 는 세 층

| 층 | 담는 것 | 누가 채울 수 있나 |
|---|---|---|
| 1층 겉모습 | 컬러 토큰, 타이포, 간격과 모서리, 컴포넌트 규격 | 레퍼런스 파일, 피그마 변수, 기존 화면에서 가져올 수 있음 |
| 2층 행동 | 상태 규칙(빈, 오류, 처리 중, 불가), 카피 톤, 누른 뒤의 피드백 | 우리 제품을 아는 사람만 |
| 3층 검증 | 숫자로 쓴 규칙, 이름을 붙인 금지 사항, 대비 수치, 버전과 날짜 | 디자이너가 문장을 "채점 가능하게" 고쳐야 생김 |

레퍼런스 md 는 1층까지만 줍니다. 2층과 3층이 실무와 시안을 가릅니다.

진단: `/design-check` (또는 `node scripts/design-check.mjs`)

## 4. AI가 지키는 문장으로 쓰는 일곱 가지 방법

1. **느낌을 숫자로.** "가독성 있게" 대신 "보조 글자는 Muted, 바탕 위 4.5:1 이상, 12 미만 금지".
2. **금지에는 이름을 붙인다.** "과하지 않게" 대신 "파랑, 보라, 그라데이션을 추가하지 않는다". 모델이 자주 지어내는 것을 콕 집어 적을수록 잘 지켜집니다.
3. **이유를 한 줄.** "Error 는 글자색으로 쓰지 않는다. 대비가 부족하기 때문." 이유가 있어야 처음 보는 상황에서도 맞게 판단합니다.
4. **이름을 코드와 맞춘다.** 피그마에서는 `color`, 코드에서는 `colorScheme` 이면 AI가 둘을 잇지 못합니다. 토큰과 컴포넌트 이름은 한 가지로.
5. **짧게.** 이 파일은 매번 통째로 읽힙니다. 한 기업의 실험에서는 80KB 짜리 DESIGN.md 만 쓴 경우가 필요한 것만 불러오는 방식보다 토큰을 약 92% 더 썼습니다. 컴포넌트 상세는 다른 파일로 빼고 여기서는 가리키기만 합니다.
6. **잴 수 있는 것은 기계에게.** 대비, 터치 영역, 토큰 밖 컬러는 글로 당부하지 말고 측정 도구와 훅으로 막습니다.
7. **버전과 날짜.** 규칙을 고칠 때마다 한 줄. 루프 기록과 맞춰 보면 어떤 규칙이 효과가 있었는지 알 수 있습니다.

## 5. 만드는 순서

1. 1층을 가져온다. 방법은 셋 중 하나.
   - 피그마 변수와 텍스트 스타일을 복사해 붙여 넣는다 (`/design-md`)
   - 피그마를 연결해 읽어 오게 한다 (`docs/figma-track.md`)
   - 분위기가 비슷한 레퍼런스 파일에서 시작해 값을 우리 것으로 바꾼다
2. `/design-check` 로 진단한다. 2층이 비어 있을 것이다.
3. 2층을 쓴다. 최근 프로젝트에서 개발 단계에 "이 화면 없는데요"가 나왔던 상태부터.
4. 3층으로 고친다. 문장마다 "화면을 보고 예 / 아니오로 답할 수 있나"를 묻는다.
5. 화면을 만들어 보고, 리뷰에서 반복되는 지적을 규칙으로 올린다. 한 번에 완성하지 않는다.

## 6. 한 파일로 부족해질 때

| 방식 | 언제 | 특징 |
|---|---|---|
| DESIGN.md | 시작, 빠른 시안, 도구를 옮겨 다닐 때 | 한 파일. 어디서나 읽힘. 길어지면 비용이 큼 |
| 스킬 | 반복하는 절차가 생겼을 때 | 필요할 때만 불려 옴. 팀이 같은 절차를 공유 |
| MCP | 실제 컴포넌트 라이브러리가 있을 때 | 에이전트가 컴포넌트 문서를 조회. 지어내기를 막기 좋음 |

대형 디자인 시스템 팀들은 대체로 셋을 같이 씁니다. 시작은 DESIGN.md 한 장으로 충분합니다.
