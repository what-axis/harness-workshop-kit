# 에이전트 구조 제안

## 에이전트란

챗봇은 한 번 묻고 한 번 답합니다. 에이전트는 목표를 받으면 **읽고, 행동하고, 결과를 확인하는 일을 스스로 반복**합니다.

| 부품 | 뜻 | 이 키트에서 |
|---|---|---|
| 모델 | 판단하는 두뇌 | Claude |
| 도구 | 손. 파일 읽기와 쓰기, 명령 실행, 브라우저 | 화면 저장, 스크린샷, 측정 |
| 지침과 기억 | 글로 쓴 파일 | `CLAUDE.md`, `DESIGN.md`, `.claude/agents/*.md` |

서브에이전트는 **역할이 정해진 담당자**입니다. 파일 하나가 담당자 한 명이고, 자기 지침만 읽은 새 대화에서 일합니다. 그래서 만든 사람의 사정을 모르는 "새 눈"이 됩니다.

## 구조 세 가지

### A. 혼자 (담당자 1명 + 체크리스트)

```
나 → designer → 화면
         ↑ DESIGN.md, 체크리스트
```

- 언제: 화면 한두 장, 틀려도 금방 고칠 수 있는 일, 아이디어 탐색
- 장점: 빠르고 쌉니다
- 한계: 스스로 채점하면 후합니다. 빠진 화면을 스스로 찾지 못합니다

프롬프트:

```
designer 에이전트로 02_define/brief.md 의 화면을 만들어줘. 끝나면 04_deliver/qa-checklist.md 를 보고 스스로 빠진 것을 표로 정리해줘.
```

### B. 둘 (만드는 담당자 + 채점하는 담당자)

```
나 → designer → 화면 → reviewer → 리포트
        ↑______________ 수정 지시 ______|
```

- 언제: 기준이 분명한 일, 화면 서너 장, 디자인 시스템 준수가 핵심일 때
- 장점: 만든 쪽과 채점하는 쪽이 갈라집니다. 구조가 단순해 설명하기 쉽습니다
- 한계: 없는 화면은 채점되지 않습니다. 사람이 루프를 직접 돌려야 합니다

프롬프트:

```
designer 와 reviewer 두 에이전트만 써서 진행해줘. designer 가 화면을 만들고, reviewer 가 04_deliver/rubric.md 로 채점하고, 미달 항목만 designer 가 고친다. 최대 3번 반복하고 매번 점수를 04_deliver/log.md 에 한 줄씩 남겨줘.
```

### C. 팀 (designer, reviewer, qa, director) · 이 키트의 기본

```
            director (순서, 기록, 멈춤)
           /     |      \
     designer  reviewer   qa
        ↑__ 수정 지시, 누락 목록 __|
사람: 기준 승인 · 직접 볼 항목 · 최종 승인
```

- 언제: 플로우 단위(여러 상태), 개발로 넘어갈 화면, 팀이 반복해서 쓸 구조
- 장점: 빠진 화면까지 잡습니다. 멈추는 규칙이 있어 끝없이 돌지 않습니다
- 한계: 시간이 더 들고 사용량이 많습니다. 기준(채점표)이 부실하면 열심히 틀립니다

실행: `claude --agent director` 로 접속한 뒤 "루프를 시작해줘."

## 무엇을 고를까

| | 틀려도 금방 고침 | 틀리면 비쌈 (개발 전달, 대외 공개) |
|---|---|---|
| 화면 한두 장 | A | B |
| 플로우 전체 | B | C |

작게 시작해서 필요할 때 담당자를 늘립니다. 담당자가 많을수록 좋은 것이 아닙니다. 담당자 하나하나는 "모델이 혼자서는 이것을 못 한다"는 가정이고, 모델이 좋아지면 그 가정은 낡습니다. 분기마다 담당자나 규칙을 하나 빼 보고 결과가 그대로인지 확인하세요.

## 팀을 늘린다면

| 담당자 | 맡는 일 | 추가할 신호 |
|---|---|---|
| researcher | 인터뷰와 데이터에서 인사이트, 인용 검증 | 리서치 자료가 많고 인용 오류가 반복될 때 |
| ux-writer | 문구만 따로 검토. 카피 톤, 오류 문장 | 리뷰에서 문구 지적이 절반을 넘을 때 |
| a11y-auditor | 접근성만 깊게. 읽는 순서, 포커스, 대체 텍스트 | 공공, 금융처럼 기준이 엄격할 때 |
| handoff | 개발 전달 문서와 이름 대응표 | 개발자가 같은 질문을 반복할 때 |

해외 사례 한 가지: 디자인 시스템 컴포넌트를 만드는 8인 파이프라인(이해 3명, 제작 3명, 검증 2명)이 공개돼 있습니다. 담당자마다 산출물, 끝났다는 기준, 재시도 횟수가 정해져 있고, 입력 품질이 낮거나 판단이 필요한 곳에서는 멈춰서 사람을 기다립니다. 구조가 커져도 원칙은 같습니다.

## 담당자를 새로 만들 때 꼭 적는 다섯 가지

1. 역할 한 줄
2. 시작할 때 읽는 파일
3. 하지 않는 것 (다른 담당자의 일)
4. 결과물의 파일 이름과 형식
5. 끝났다고 보는 기준, 멈추고 사람에게 묻는 경우

틀: `templates/agent-template.md`

프롬프트:

```
templates/agent-template.md 를 바탕으로 우리 팀에 필요한 담당자 한 명을 .claude/agents/ 에 만들어줘. 만들기 전에 나에게 세 가지를 하나씩 물어봐: 이 담당자가 맡을 일, 하지 말아야 할 일, 끝났다고 볼 기준.
```

## 신뢰 수준은 담당자가 아니라 행동마다

| 행동 | 권장 |
|---|---|
| 화면 초안 만들기, 리포트 쓰기 | 자동 |
| 화면 고치기 | 자동. 단, 루프 횟수 제한과 기록 |
| DESIGN.md, 채점표 고치기 | 제안만. 사람이 승인 |
| 피그마 팀 파일에 쓰기, 개발 저장소에 반영 | 초안까지. 사람이 확인 후 반영 |
