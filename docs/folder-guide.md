# 폴더 지도, 스킬 만들기, 내 자료 넣는 곳

이 문서는 키트를 내려받은 뒤 "여기에 뭐가 있고 왜 이렇게 생겼는지"를 알고 시작하기 위한 안내입니다.

## 1. 먼저 하는 한 줄: npm run doctor

```
npm install
npm run doctor
```

- `npm install` 은 이 폴더에서 한 번만 합니다. 화면을 스크린샷으로 찍고 숫자를 재는 도구(playwright-core)를 내려받습니다. 브라우저는 새로 받지 않고 이미 깔린 크롬이나 엣지를 씁니다.
- `npm run doctor` 는 실습 준비가 됐는지 점검만 합니다. 파일을 바꾸지 않습니다. 확인하는 것은 네 가지입니다.
  1. Node.js 18 이상이 있는가
  2. Claude Code 가 설치돼 있는가
  3. 키트의 필수 파일이 빠짐없이 있는가
  4. 브라우저가 자동으로 열려서 스크린샷과 측정이 되는가
- `[통과]` 가 네 개 나오면 준비 완료입니다. `[확인 필요]` 가 나오면 바로 아래 화살표(->) 줄이 고치는 방법입니다.

## 2. 폴더는 이렇게 생겼습니다

```
harness-workshop-kit/
├─ CLAUDE.md          AI가 매번 먼저 읽는 안내서. 말투, 규칙, 폴더 지도
├─ DESIGN.md          디자인 규칙을 AI가 읽는 글로 쓴 한 파일
├─ 00_inputs/         재료. 기획서, 인터뷰 기록 (AI는 읽기만 합니다)
├─ 01_discover/       찾기: 인사이트, 내 판단 기준, 유사 사례
├─ 02_define/         정하기: 브리프, 가설, 검증 항목
├─ 03_develop/        만들기: screens/ 화면 HTML, shots/ 스크린샷
├─ 04_deliver/        전달: 채점표, QA 목록, 리포트, 점수 기록(log.md)
├─ .claude/
│   ├─ agents/        담당자 4명 (designer, reviewer, qa, director)
│   ├─ skills/        절차 10개 (/brief, /rubric, /measure ...)
│   └─ settings.json  허용해 둔 명령 목록
├─ scripts/           숫자를 재는 도구 (measure, shot, design-check, doctor)
├─ templates/         내 담당자, 내 하네스 카드를 만들 때 쓰는 틀
├─ examples/          완성 예시(before, after)와 단계별 따라잡기 파일
└─ docs/              DESIGN.md 쓰는 법, 에이전트 구조, 피그마 연결, 훅
```

## 3. 왜 이렇게 만들었나

| 결정 | 이유 |
|---|---|
| 번호 폴더 `00`~`04` | 디자이너에게 익숙한 더블 다이아몬드(찾기, 정하기, 만들기, 전달) 순서 그대로입니다. 파일을 어디에 넣을지 새로 외울 필요가 없습니다. 번호 순서대로 따라가면 일이 됩니다 |
| 한 폴더에 한 단계 | AI에게 "이 폴더만 읽어"라고 시킬 수 있고, 결과가 어디에 남는지 예측이 됩니다. 단계가 뒤엉키지 않습니다 |
| 결과물이 전부 파일 | AI의 기억은 대화가 길어지면 흐려집니다. 파일에 남기면 대화를 비워도(`/clear`) 이어서 일할 수 있습니다 |
| `00_inputs` 는 읽기만 | 원본 자료를 AI가 고치는 사고를 막습니다. 내 자료가 안전합니다 |
| 만드는 곳과 채점하는 곳 분리 | `03_develop` 에는 화면만, `04_deliver` 에는 점수와 리포트만 둡니다. 만든 사람이 채점하지 않는다는 원칙이 폴더로도 보입니다 |
| `CLAUDE.md` 가 맨 위 | AI가 폴더에 들어오면 가장 먼저 읽는 파일입니다. 말투와 규칙을 한 번만 적으면 모든 대화에 적용됩니다 |
| `.claude/` 안에 담당자와 절차 | 클로드 코드가 이 위치를 자동으로 찾도록 정해진 자리입니다. 폴더 이름과 위치를 바꾸면 인식되지 않습니다 |
| `scripts/` 는 기계가 쓰는 도구 | 대비, 터치 크기 같은 숫자는 AI의 눈이 아니라 코드로 잽니다. AI에게 "재 줘"라고 하면 이 도구를 실행합니다 |
| `examples/` 는 고치지 않음 | 막혔을 때 복사해 쓰는 정답지입니다. 원본이 그대로 있어야 합니다 |

## 4. 담당자와 스킬이 다른 점

| | 담당자 (agents) | 스킬 (skills) |
|---|---|---|
| 비유 | 팀원 한 명 | 업무 매뉴얼 한 장 |
| 위치 | `.claude/agents/이름.md` | `.claude/skills/이름/SKILL.md` |
| 부르는 법 | "designer 에이전트로 ..." 라고 말하거나 `claude --agent director` | `/이름` |
| 하는 일 | 따로 일하고 결과 파일을 남김. 자기만의 대화 공간에서 일함 | 지금 대화 안에서 정해진 순서대로 일함 |
| 언제 만드나 | 만드는 눈과 채점하는 눈을 나눠야 할 때 | 같은 절차를 매번 설명하게 될 때 |

## 5. 스킬은 이렇게 생겼습니다 (/brief 를 예로)

파일 위치는 `.claude/skills/brief/SKILL.md` 입니다. 폴더 이름이 곧 슬래시 명령 이름입니다.

```markdown
---
name: brief
description: Define 단계. 인사이트와 판단 기준을 브리프 한 장으로 압축한다. 가설마다 검증 항목을 붙인다.
disable-model-invocation: true
---

# 브리프와 가설 만들기

(1) 무엇을 읽는지  (2) 지켜야 할 규칙  (3) 결과 형식  (4) 끝난 뒤 확인할 것  (5) 다음 단계 안내
```

맨 위 `---` 사이가 머리말입니다.
- `name`: 슬래시 뒤에 쓰는 이름입니다.
- `description`: 이 스킬이 무엇이고 언제 쓰는지 한두 문장입니다. 클로드가 이 줄을 보고 목록에 띄웁니다.
- `disable-model-invocation: true`: 사람이 `/이름` 으로 부를 때만 실행합니다. AI가 멋대로 부르지 않게 하려고 넣었습니다.

그 아래 본문은 평범한 글입니다. 이 키트의 스킬은 모두 같은 다섯 칸으로 씁니다.
1. 무엇을 읽는가 (입력 파일)
2. 지켜야 할 규칙
3. 결과 형식 (어떤 파일을 어떤 모양으로 남기는가)
4. 끝나고 스스로 확인할 점검 목록
5. 다음에 칠 한 줄

## 6. 내 스킬 만들기

가장 쉬운 방법은 클로드에게 시키는 것입니다. 템플릿은 `templates/skill-template.md` 에 있습니다.

```
templates/skill-template.md 를 바탕으로 내 업무용 스킬을 .claude/skills/ 에 만들어줘. 만들기 전에 나에게 네 가지를 하나씩 물어봐: 이 절차를 부르는 이름, 무엇을 읽는지, 결과를 어떤 파일에 어떤 모양으로 남기는지, 끝났다고 보는 기준.
```

좋은 스킬의 조건:
- **내가 같은 설명을 세 번 넘게 했다** 면 스킬로 만들 때입니다.
- 결과는 **파일**로 남깁니다. 대화 속에 말로만 남기지 않습니다.
- 규칙은 예, 아니오로 확인할 수 있게 씁니다. ("깔끔하게"가 아니라 "주 버튼은 한 화면에 하나")
- 끝에 다음 단계를 한 줄로 알려 주게 합니다.

만든 뒤에는 `/이름` 을 쳐서 목록에 뜨는지 확인하고, 한 번 돌려 보고 결과 파일이 기대한 모양인지 봅니다. 목록에 안 뜨면 폴더 이름과 `SKILL.md` 파일 이름(대문자)을 확인하세요.

## 7. 내가 작업 중인 자료를 가져온다면

| 내 자료 | 넣는 곳 | 설명 |
|---|---|---|
| 기획서, PRD, 요구사항 | `00_inputs/` | 오늘 쓰는 `product-brief.md` 를 내 기획서로 바꿔도 되고, 파일을 하나 더 넣어도 됩니다 |
| 사용자 인터뷰, 설문, 고객 문의 | `00_inputs/interviews/` | 한 사람이 한 파일. 텍스트나 마크다운이 가장 좋습니다 |
| 회사 디자인 가이드, 토큰 표 | `DESIGN.md` 를 고치거나 `/design-md` 로 변환 | 가이드 문서나 피그마 변수를 붙여 넣으면 세 층 구조로 바꿔 줍니다 |
| 기존 화면 (HTML) | `03_develop/screens/` | `번호-이름.html` 로 한 파일에 한 화면 상태 |
| 기존 화면 (이미지, 피그마 캡처) | `00_inputs/screens/` (폴더를 새로 만드세요) | 레퍼런스로 읽게 합니다. 화면 파일로 취급하지 않습니다 |
| 우리 팀 리뷰 지적, 체크리스트 | `04_deliver/rubric.md` 를 고치기 | 지적을 예, 아니오 문장으로 바꿔 항목에 넣습니다 |

주의할 점:
- 회사 자료는 **공개해도 되는지 확인**하고 넣으세요. 이 폴더를 깃허브에 올리면 함께 올라갑니다.
- 가장 안전한 방법은 이 키트를 **내 컴퓨터의 새 폴더에 복사**해서 쓰고, 이 저장소와는 연결하지 않는 것입니다.
- 개인정보가 들어 있는 인터뷰는 이름과 연락처를 지운 뒤 넣으세요.
- 내 자료로 바꿀 때는 `CLAUDE.md` 의 서비스 설명 한 줄, `00_inputs/product-brief.md`, `DESIGN.md` 이 세 곳을 먼저 바꾸면 나머지는 따라옵니다.
- 오늘 만든 결과가 섞이지 않도록, 새 과제는 키트를 한 번 더 복사해서 시작하는 것을 권합니다.
